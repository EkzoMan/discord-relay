# Discord Relay

Бот-ретранслятор для Discord: читает сообщения из выбранных **исходных каналов**
одного сервера и пересылает их через **webhook** в другой Discord-сервер.
Управление каналами-маппингами выполняется через простой web-интерфейс
(FastAPI + Jinja2) — без перезапуска бота.

Каждый маппинг — это правило «канал → webhook»: сообщение, опубликованное в
исходном канале, появляется в целевом канале от имени исходного автора
(имя и аватар сохраняются), а вложения передаются ссылками в блоке
`Вложения:`.

## Основные возможности

- **Web-интерфейс**: добавление, удаление и тестирование маппингов; изменения
  вступают в силу сразу (бот читает хранилище при каждом входящем сообщении).
- **Сохранение автора**: пересылаются имя (display name) и аватар автора
  сообщения; длина урезается под лимиты Discord (username ≤ 80, контент ≤ 2000 символов).
- **Вложения**: ссылки на вложения добавляются к тексту под заголовком `Вложения:`.
- **Без нежелательных пингов**: пересылаемый контент отправляется с
  `allowed_mentions: {"parse": []}` — упоминания `@role`/`@everyone` не срабатывают.
- **Защита от петель**: сообщения, созданные webhook'ами (в том числе вашим же
  ботом-ретранслятором), всегда игнорируются; сообщения от ботов игнорируются
  по умолчанию (см. `RELAY_ALLOW_BOT_MESSAGES`).
- **Безопасное хранение секретов**: webhook URL отображается в UI замаскированным,
  в логи не попадает; принимаются только настоящие URL Discord-webhook
  (`https://discord.com/api/webhooks/...` или `https://discordapp.com/api/webhooks/...`).
- **Валидация**: идентификатор канала — только положительное число (snowflake);
  один пользователь не может добавить два релея на один канал, но разные
  пользователи могут зарегистрировать один и тот же канал — каждый получит
  свою копию сообщений (fan-out на несколько webhook'ов).
- **Персистентность**: пользователи, сессии и релеи хранятся в **SQLite**
  (`RELAY_DB_PATH`, в Docker — на томе `/data`). Старый JSON-конфиг
  (`RELAY_CONFIG_PATH`) автоматически импортируется один раз при первом старте
  и становится owned bootstrap-администратором; повторных импортов нет.
- **Многопользовательская авторизация по сессиям**: вход через веб-форму,
  cookie `HttpOnly`/`SameSite=lax`. Обычные пользователи видят и управляют
  **только своими** релеями; администраторы видят релеи всех пользователей
  (с колонкой «Владелец») и управляют учётными записями
  (`ADMIN_USERNAME` / `ADMIN_PASSWORD`).
- **Работает в двух режимах**: UI-only без токена (для отладки) или полный
  relay с токеном бота.

## Требования

- **Python 3.12** (зависимости зафиксированы под эту версию в `requirements.txt`:
  `discord.py`, `fastapi`, `uvicorn[standard]`, `httpx`, `jinja2`,
  `python-multipart`, `pydantic`; для тестов — `pytest`, `pytest-asyncio`).
- Либо **Docker + Docker Compose** (образ `python:3.12-slim`, контейнер работает
  под непривилегированным пользователем `relay`).
- Аккаунт Discord с правами на создание приложения
  ([developer portal](https://discord.com/developers/applications)) и
  права администратора сервера для создания webhook.
- В исходящем направлении нужен только HTTPS-доступ к `discord.com`
  (webhook API); БД и внешние сервисы не требуются.

## Настройка Discord-приложения (пошагово)

1. Откройте <https://discord.com/developers/applications> →
   **New Application**, задайте имя.
2. Вкладка **Bot** → **Reset Token** → скопируйте токен
   (показывается один раз) — это значение `DISCORD_BOT_TOKEN`
   (см. также раздел «Получение DISCORD_BOT_TOKEN» ниже).
3. **Обязательно**: на той же вкладке **Bot**, блок *Privileged Gateway Intents*,
   включите **MESSAGE CONTENT INTENT** и сохраните. Без этой настройки бот
   будет видеть пустой текст сообщений — пересылка содержимого невозможна.
4. Вкладка **OAuth2 → URL Generator**:
   - Scopes: `bot`;
   - Bot Permissions: **View Channels** (бот не пишет сообщения в исходный
     сервер — он только читает каналы и отправляет в webhook, поэтому право
     *Send Messages* на исходном сервере не требуется).
5. Скопируйте сгенерированную ссылку, откройте её в браузере и добавьте бота
   на сервер с **исходными** каналами. Убедитесь, что бот имеет доступ к нужным
   каналам (для приватных каналов — соответствующие права).

### Получение DISCORD_BOT_TOKEN

Токен берётся из developer portal: приложение → **Bot → Reset Token**.
Reset генерирует новый токен и **аннулирует старый**. Если токен скомпрометирован —
сразу сделайте Reset. Токен — секрет: передавайте его только через переменные
окружения, не коммитьте в git и не вставляйте в переписку.

### Получение webhook URL (целевой канал)

На сервере, **куда** нужно пересылать сообщения:

1. Настройки сервера → **Integrations → Webhooks** → **New Webhook**.
2. Выберите целевой канал, при желании настройте имя/аватар webhook'а.
3. **Copy Webhook URL** — скопируйте ссылку вида
   `https://discord.com/api/webhooks/<id_канала>/<секретный_токен>`.

Последний сегмент URL — секретный токен: тот, кто знает полный URL, может
писать в канал. Храните его как пароль (UI показывает только первые 8 символов токена).

### Как узнать ID исходного канала

В Discord: Настройки пользователя → **Advanced** → включите **Developer Mode**.
После этого: правый клик по каналу → **Copy Channel ID**.

## Переменные окружения

| Переменная | По умолчанию | Описание |
| --- | --- | --- |
| `DISCORD_BOT_TOKEN` | *(пусто)* | Токен бота. Обязателен для пересылки; без него работает только web-UI (в логах — предупреждение, статус «Бот выключен»). |
| `RELAY_DB_PATH` | `/data/relay.db` | SQLite-файл с пользователями, сессиями и релеями (stdlib `sqlite3`). В Docker `/data` — volume. **При локальном запуске на Windows задайте локальный путь**, например `./data/relay.db`. |
| `RELAY_CONFIG_PATH` | `/data/config.json` | **Только устаревший JSON-конфиг**: при первом старте его маппинги импортируются в SQLite и становятся релеями bootstrap-администратора. Дальше файл не используется. |
| `PORT` | `8000` | Порт uvicorn. В `docker-compose.yml` проброс зафиксирован как `8000:8000` — при изменении `PORT` синхронно поменяйте маппинг портов. |
| `ADMIN_USERNAME` | `admin` | Логин bootstrap-администратора. |
| `ADMIN_PASSWORD` | *(пусто)* | Пароль bootstrap-администратора. **Настоятельно рекомендуется задать.** Если задан — админ создаётся при первом старте (существующий пароль **никогда не перезаписывается**). Если **не задан и пользователей в базе нет** — создаётся пара `admin`/`admin` с громким предупреждением в логе; это общедоступный credential, смените его немедленно после первого входа (для любого хоста, кроме 127.0.0.1, оставляйте `ADMIN_PASSWORD` пустым только осознанно). Пароль длиннее 1024 символов будет отклонён при старте с ошибкой в логе. |
| `SESSION_COOKIE_NAME` | `relay_session` | Имя cookie сессии. |
| `SESSION_TTL_HOURS` | `168` | Время жизни сессии (по умолчанию 7 суток). |
| `SESSION_COOKIE_SECURE` | `auto` | Флаг `Secure` у cookie сессии: `auto` — ставится при HTTPS-запросе (в т.ч. по заголовку `X-Forwarded-Proto`), `true` — всегда, `false` — никогда (только локальный отладочный HTTP). |
| `LOGIN_MAX_ATTEMPTS` | `10` | Неудачных входов с одной пары «логин + IP-клиент» в окне `LOGIN_LOCKOUT_MINUTES`, после которых включается блокировка перебора. |
| `LOGIN_LOCKOUT_MINUTES` | `15` | Окно подсчёта неудач и время блокировки входа (минуты). Успешный вход сбрасывает счётчик. |
| `UI_USERNAME` / `UI_PASSWORD` | *(пусто)* | **Устарело** (бывший опциональный HTTP Basic Auth). Если `ADMIN_PASSWORD` не задан, а обе переменные заданы, они используются как bootstrap-пароль администратора с предупреждением в логе. |
| `RELAY_ALLOW_BOT_MESSAGES` | `false` | `true` — пересылать также сообщения авторов-ботов. Сообщения от webhook'ов игнорируются всегда (защита от петель). |
| `RELAY_ALLOW_WEBHOOK_MESSAGES` | `false` | `true` — пересылать также сообщения авторов-вебхук. Сообщения от webhook'ов игнорируются всегда (защита от петель). |
| `RELAY_LOG_LEVEL` | `INFO` | Уровень логирования: `DEBUG`, `INFO`, `WARNING`, `ERROR`. |

Значения `RELAY_ALLOW_BOT_MESSAGES`, принимаемые как «истина»: `1`, `true`,
`yes`, `on` (без учёта регистра). Пустая строка трактуется как «не задано».

## Запуск локально через Python

```powershell
# из корня проекта (PowerShell)
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt

# настройки передаются через переменные окружения:
$env:DISCORD_BOT_TOKEN   = "<токен бота>"          # можно не задавать для UI-only
$env:RELAY_DB_PATH       = "./data/relay.db"        # на Windows смените default /data/...
$env:PORT                = "8000"                  # необязательно
$env:ADMIN_USERNAME      = "admin"                 # bootstrap-администратор
$env:ADMIN_PASSWORD      = "<стойкий пароль>"      # см. поведение при пустом значении
$env:RELAY_ALLOW_BOT_MESSAGES = "false"
$env:RELAY_LOG_LEVEL     = "INFO"

python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
# альтернатива: python -m app.main  (порт берётся из $env:PORT)
```

Откройте <http://localhost:8000> — приложение перенаправит на `/login`.
Войдите под `ADMIN_USERNAME`/`ADMIN_PASSWORD` (если пароль не задан и база
пуста — это `admin`/`admin`, **смените пароль сразу** через «Смена пароля»).

> **Важно:** приложение **не читает файл `.env`** — `.env` предназначен только
> для `docker compose` (`env_file`). При локальном запуске экспортируйте
> переменные в оболочку, как показано выше (в Linux/macOS: `export VAR=...`).

## Запуск через Docker / docker compose

```bash
# 1. Создайте .env на основе примера и заполните значения
copy .env.example .env        # Windows
# cp .env.example .env        # Linux/macOS
notepad .env                  # заполните DISCORD_BOT_TOKEN, ADMIN_PASSWORD и опции

# 2. Соберите и запустите
docker compose up -d --build

# 3. Смотрите логи подключения и пересылки
docker compose logs -f

# Остановка (база останется в volume relay-config)
docker compose down
```

Нюансы compose-варианта:

- Без файла `.env` `docker compose` не запустится (он указан в `env_file`).
- SQLite-база (`relay.db` + WAL-файлы) хранится в именованном volume
  `relay-config` внутри контейнера по пути `/data/relay.db` — переживает
  `docker compose down` и пересборку образа. Если в volume остался старый
  `config.json`, он будет импортирован один раз при первом новом старте.
- Контейнер работает под непривилегированным пользователем (uid 10001).
- Порт хоста зафиксирован: `http://localhost:8000`.

## Web-интерфейс

Вход — на `/login` (логин + пароль). Все маршруты, кроме `/login` и `/health`,
требуют активную сессию (cookie). Шапка показывает текущего пользователя и его
роль; ссылки: Панель, Смена пароля, Админ-панель (для админа), Выход.

Дашборд на `/` для **любого** пользователя:

1. **Статус** — состояние бота (`Подключён` / `Подключение` / `Бот выключен`) и
   число релеев (у админа — и своих, и суммарно по всем).
2. **Мои релеи** — таблица **только собственных** правил: имя, ID канала,
   маскированный webhook URL, кнопки **Тест**/**Удалить**.
3. **Все релеи пользователей** (только для админа) — правила всех пользователей
   с колонкой **Владелец**; админ может тестировать и удалять чужие релеи.
4. **Добавить реле** — форма (владельцем записи становится вошедший пользователь;
   указать «чужого» владельца через форму нельзя).

Админ-панель `/admin/users`: создание пользователей (роль `user`/`admin`),
включить/отключить аккаунт (нельзя отключить самого себя), сброс пароля
после которого сессии пользователя завершаются.

Действия сохраняются в SQLite сразу, применяются мгновенно (бот читает хранилище
при каждом входящем сообщении) — перезапуск не нужен.

JSON-эндпоинты: `GET /status` (требует авторизацию; возвращает текущего
пользователя, статус бота и число **видимых** релеов; webhook URL и хэши
паролей не отдаются) и `GET /health` (`{"status": "ok"}`, публичный).

## Как проверить, что всё работает

1. **Тесты** (не требуют сети и токена):

   ```powershell
   python -m pytest -q
   ```

2. **Запустите приложение** (локально или `docker compose up -d`), откройте
   <http://localhost:8000> — войдите администратором; статус должен стать
   `Подключён` (в логах: `Relay bot connected as <bot> (id=...)`).
   Проверить публичный эндпоинт: `curl http://localhost:8000/health`.
3. **Тест релея**: в таблице нажмите **Тест** — в целевом канале появится
   сообщение «🔔 Test message from Discord Relay…», а на дашборде — зелёное
   уведомление «Test message sent».
4. **Сквозная проверка**: напишите сообщение в исходный канал — оно должно
   появиться в целевом от имени автора с его аватаром; вложения — блоком
   `Вложения:` со ссылками. В логах — строка `Relayed message <id> from
   channel <id> via mapping <id>`.
5. **Типичные причины, почему не работает**:
   - не включён **Message Content Intent** → бот не видит текст сообщений,
     пересылка содержимого невозможна;
   - бот не добавлен на сервер исходного канала или не видит канал;
   - неверный/отозванный токен → `Discord rejected DISCORD_BOT_TOKEN` в логах;
   - webhook удалён или изменён → `Webhook rejected the message with HTTP 404`
     (или иной статус).

## Безопасность

- **Не храните токены и webhook-URL в репозитории.** Секреты передаются только
  через переменные окружения. Файлы `.env`, `data/` и `config.json` уже
  исключены в `.gitignore`; в репозитории лежит только `.env.example` без значений.
- **Сессионная авторизация обязательна всегда**: вход по логину/паролю,
  токен сессии — в cookie `HttpOnly` + `SameSite=lax` (`Secure` — по политике
  `SESSION_COOKIE_SECURE`: `auto` ставит флаг при HTTPS / `X-Forwarded-Proto`,
  `true` — всегда, `false` — никогда, только для локального отладочного HTTP).
  В БД хранится только SHA-256 от токена, поэтому утечка базы не даёт живых
  сессий.   Пароли — PBKDF2-HMAC-SHA256 с индивидуальной солью и 210 000 итераций;
  сравнение через `secrets.compare_digest`. Ошибки входа одинаковы для
  «нет такого пользователя» и «неверный пароль»; dummy-хэш для неизвестного
  логина считает те же `PBKDF2_ITERATIONS`, поэтому время ответа не выдаёт
  существование аккаунта. Логины/пароли неудачных попыток в лог не пишутся.
- **Троттлинг входа (перебор паролей)**: после `LOGIN_MAX_ATTEMPTS` (default 10)
  неудачных попыток для пары «логин + IP клиента» включается блокировка на
  `LOGIN_LOCKOUT_MINUTES` (default 15) — ответ HTTP 429 с общим сообщением
  «Too many login attempts. Try again later.»; в окне блокировки отклоняются
  даже корректные credentials, а успешный вход сбрасывает счётчик.
- **Ограниченная стоимость хэширования**: пароль длиннее 1024 символов
  отвергается на границах ввода (создание пользователя, смена и сброс пароля —
  явная ошибка; на входе — общий «неверный логин или пароль») и не доходит до
  PBKDF2. Уже сохранённые хэши существующих паролей остаются рабочими —
  лимит не требует перехэширования/миграции.
- **Отключённый пользователь не ретранслирует**: горячий путь бота
  (`get_all_by_channel`) SQL-JOIN'ом отсеивает релеи владельцев с выключенной
  учётной записью — деактивация мгновенно останавливает релей; при этом
  админ продолжает видеть такие релеи в списке «Все релеи пользователей»
  (надзор ≠ исполнение).
- **Разграничение доступа**: обычный пользователь видит/удаляет/тестирует только
  свои релеи; админ — все. Проверки выполняются в слое хранилища, ответы для
  «чужого» и «несуществующего» id одинаковые (без утечки существования).
  Владелец релея всегда берётся из сессии, а не из формы.
- **Bootstrap-админ**: задавайте `ADMIN_PASSWORD` в `.env` всегда. Если он
  пуст и пользователей в базе нет, приложение convenience-фолбэком создаёт
  `admin`/`admin` и орёт об этом предупреждением в лог — такую базу можно
  оставлять только за NAT/127.0.0.1, сменить пароль нужно немедленно после
  первого входа. Если `ADMIN_PASSWORD` задан, пароль существующего админа
  не перезаписывается никогда (фолбэк `admin`/`admin` при этом не срабатывает).
- **Маскирование webhook URL**: в дашборде показывается только префикс токена
  (8 символов), полный URL нигде в UI/JSON не отображается и **не попадает в логи**
  (логируются лишь классы ошибок HTTP и статусы ответов).
- **Валидация webhook URL**: принимаются только адреса настоящих Discord
  webhooks — нельзя указать произвольный URL («утечка» данных на сторонний сервер
  через UI отклоняется).
- **Отсутствие ping'ов**: пересылаемый контент не может упомянуть `@everyone`/роли.
- **Защита от циклов**: webhook-сообщения игнорируются всегда; бот-сообщения —
  по умолчанию.
- **Контейнер** работает от непривилегированного пользователя; запись в SQLite
  идёт транзакциями (WAL), сбой не оставляет «полупроведённых» изменений.
- HTTP не шифрует трафик: пароли и cookie летят открытым текстом — выставляйте
  интерфейс наружу только через reverse-proxy с TLS, а не напрямую.

## Ограничения MVP

- **Нет очереди повторных попыток при HTTP 429 и других ошибках**: если
  Discord отклонил пост (rate limit, удалённый webhook, сети нет), сообщение
  **теряется** — фиксируется только предупреждение в логе.
- **Нет CSRF-защиты**: формы UI не содержат CSRF-токенов; частично это
  компенсируется cookie `SameSite=lax`, но при публичном доступе держите
  интерфейс за reverse-proxy.
- **Rate-limiting входа — in-memory**: троттлинг живёт в словаре одного
  процесса (см. `app/ratelimit.py`). Работает при штатной раскладке (один
  uvicorn-воркер); при запуске в несколько воркеров/реплик счётчики
  расходятся — тогда лимитер нужно вынести в общее хранилище (interface
  уже изолирован для этого замены).
- **Пересылается только текст + ссылки на вложения**: embed'ы, стикеры,
  контекст ответов (reply), редактирования и удаления сообщений **не**
  обрабатываются; редактирование в исходном канале не обновляет пересланное
  сообщение.
- **Длинные сообщения обрезаются** до 2000 символов (не разбиваются на несколько).
- **Дубликаты релеев**: один пользователь не может добавить два релея на один
  канал; разные пользователи — могут (каждый получит свою копию). Удаление
  учётной записи не предусмотрено (только деактивация).
- **Нет встроенного TLS** — сервер отдаёт только HTTP; при выносе наружу
  шифрование обеспечивает reverse-proxy.
- Ручное редактирование старой `config.json` «на живую» не поддерживается:
  импорт выполняется **однократно** при первом старте (флаг в таблице `meta`),
  дальше источник истины — только SQLite (`relay.db`).

## Структура проекта

```
app/
  main.py        — FastAPI: маршруты UI/API, сессионная авторизация, роли, lifespan с фоновой задачей бота
  auth.py        — PBKDF2-хэширование паролей, токены сессий (stdlib)
  relay_bot.py   — discord.Client: слушает on_message, фильтрует, рассылает по всем релеям канала
  webhooks.py    — POST в Discord webhook (httpx), маскирование ошибок
  store.py       — SQLite-хранилище (users/sessions/mappings/meta) + bootstrap админа + импорт legacy JSON
  ratelimit.py   — in-memory троттлер входа (ключ: логин+IP, окно/блокировка настраиваемые)
  models.py      — Pydantic-модели (User, RelayMapping) и валидация webhook URL / канала
  settings.py    — чтение конфигурации из переменных окружения
  templates/     — base.html, login.html, index.html, admin_users.html, change_password.html (Jinja2)
tests/           — pytest-тесты (auth, store, routes, relay bot, webhooks; без сети и токена)
Dockerfile       — python:3.12-slim, non-root, RELAY_DB_PATH=/data/relay.db, CMD uvicorn с ${PORT}
docker-compose.yml — сервис + volume relay-config + env_file .env
.env.example     — шаблон переменных окружения
requirements.txt — зафиксированные зависимости (Python 3.12; SQLite — stdlib)
```

Legacy-формат JSON (импортируется однократно): `{"mappings": [{"id": "...", "name": "...", "source_channel_id": 123, "target_webhook_url": "https://discord.com/api/webhooks/..."}]}`.
